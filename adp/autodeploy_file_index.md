# PiFitness deployment — file index

**Purpose:** Inventory every file, file set, and persistent file artifact needed by the deployment workflow, what each must do, what it returns to the orchestrator, and which phase/steps consume it.

**Specification precedence:** `bootstrap_objectives.md` is the current design and governs this index: TEST has 10 steps and PRD has 9. `autodeploy_objectives.md` is the earlier design (9-step sequence) and is useful for background, but its earlier step numbering/order must not be implemented over the newer bootstrap design.

**Path convention:** Paths under `deploy/scripts/` are taken from the launcher’s temporary extraction of the selected commit. Paths under `/home/god/` are Pi-side runtime paths. Proposed helper filenames below make the modular design buildable; the objective documents require per-step helpers under `deploy/scripts/lib/` but do not prescribe their exact filenames.

The following is the proposed layout. Each step helper is sourced by the orchestrator and defines one environment-specific step function. Shared libraries provide common mechanics. Helpers should **not** print their own competing summary or install their own process-level traps.

## 6. Build-time contract gaps to resolve explicitly

The objective documents leave the following names or interfaces open. They are not reasons to block the file index, but they must be resolved before the dependent file is considered complete.

1. **Helper filenames and function names:** per-step helper locations are required, but exact names are not specified. This index proposes `test-step-NN-*` and `prd-step-NN-*` files and a sourced-function interface.
2. **`test-down.sh` location/interface:** referenced by both pre-flight steps, but no path or argument contract is supplied. This index places it at `deploy/scripts/lib/test-down.sh`.
3. **Service snapshot filename/config key:** the active-unit record must be persistent, but no explicit key/path is listed in `autodeploy.conf` or the Pi env-file table. Add a `RUN_STATE_DIR` or equivalent host-side setting before implementing service stop/restore.
4. **`deploy/tests.conf` command names:** the example uses `TEST_PYTEST`, `TEST_NPM`, and `TEST_SMOKE`, while PRD reuses the same regression and smoke suites. Choose environment-neutral command keys or explicitly document how the same keys are run with PRD environment variables.
5. **Health/version identity:** the health URL and the required `environment`/SHA response are specified, but the endpoint/header contract and application source path are not.
6. **Manual test script:** TEST Step 10 requires the developer to run it, but its filename/location/command are not specified.
7. **TEST DB marker representation:** a marker table/setting is suggested, but its exact schema and verification query are not defined.
8. **Legacy reference:** `legacy_bootstrap_parameters.md` is referenced for historical path conventions; it is documentation input, not a runtime dependency of the new orchestrator.

## 7. Helper interface contract

To keep all testing at the orchestrator boundary:

- Shared libraries and step helpers are **sourced** by `autodeploy.sh`; sourcing only defines functions/constants and does not execute deployment work. Use a stable naming convention: `test-step-NN-*.sh` defines `step_test_NN_*`; `prd-step-NN-*.sh` defines `step_prd_NN_*`.
- The orchestrator invokes the function in the current shell. A helper returns `0` only for PASS or an explicitly permitted SKIPPED outcome; non-zero means FAIL. The orchestrator owns the final status label and exit code.
- Helpers emit human-readable `EVIDENCE: key = value` lines and, on failure, a concise cause plus the command/file context. The orchestrator captures the final status and output tail for the final summary.
- Durable information needed by later steps or after a crash (database state, exact dump path, operator decision, active service set, previous checkout path) is written to explicit state files outside the app directory. Do not rely on shell variables for recovery.
- Cleanup functions are idempotent. A cleanup action that has not been registered/started must be reported as a no-op, not guessed at.
- A missing shared library is reported by its exact path as a missing/unimplemented library, and the run stops before invoking step functions; the final table must not mark any step PASS. A missing step-helper file is reported as `NOT IMPLEMENTED`, and the run stops at that step after cleanup. A present helper that fails at runtime is `FAIL`. A missing required configuration file, env file, binary, DB, or service is a startup/pre-flight `FAIL`, not `NOT IMPLEMENTED`.
