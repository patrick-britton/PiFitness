# TEST/PRD Schema Comparison

`tools/db/compare_schema.py` is a read-only structural comparator backed by
MigraDiff 1.7.2. It does not read or parse migration SQL, does not alter either
database, and never applies generated SQL.

## Configuration sources

It uses the existing application environment files:

- TEST: `/home/god/.config/pifitness/test.env`, with `APP_ENV=test`
- PRD: `/home/god/PiFitness/backend/.env`, with `APP_ENV=prod`

These are the defaults on the Pi. `--test-env-file` and `--prd-env-file` can
override the paths when necessary. No migration-specific `.env` files are used.

## Invocation

```bash
/home/god/PiFitness-test/venv/bin/python \
  /home/god/PiFitness-test/tools/db/compare_schema.py \
  --allow-prd \
  --diff-file /home/god/Documents/PiFitness_Test_Evidence/schema-diff.json
```

PRD comparison requires explicit `--allow-prd` even though the operation is
read-only. The wrapper validates the exact database names, endpoint, and
markers before invoking MigraDiff.

## Output contract

One JSON object is written to stdout:

- `ok`: whether comparison completed safely
- `status`: `identical`, `different`, or `error`
- `test` / `prd`: verified database and server identity (never credentials)
- `statement_count`: number of structural differences
- `diff_preview`: concise structural difference preview
- `scope`: objects included and intentionally excluded
- `diff_file`: included when a full diff artifact was requested

Exit code 0 means the comparison completed. It does not mean the schemas are
equal; callers must inspect `status`. Exit code 1 means the comparison could
not be completed safely.

## Comparison semantics

The wrapper invokes MigraDiff in JSON mode, with destructive changes included
for diagnostic completeness. It never passes `--apply` and never executes the
SQL generated by MigraDiff. The comparison excludes `COMMENT ON` statements
and the `schema_migrations` bookkeeping table. It does not compare ACLs or
privileges. Database roles and role memberships are cluster-level objects and
are handled separately by provisioning.

The result is directional: it asks what structural changes would transform
TEST toward PRD. Generated SQL is diagnostic output only.
