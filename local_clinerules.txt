# Error Strategy & Loop Prevention
* **The One-Attempt Rule:** If a local build tool, compilation step, or test execution fails, you are permitted exactly ONE automated attempt to diagnose and fix the root cause.
* **Constraint:** This single attempt is allowed ONLY if the fix involves isolated lines of code. If resolving the error requires restructuring major blocks of code or modifying shared system logic, you must immediately halt, drop into Plan Mode, and present the problem to the user.
* **Anti-Loop Guard:** If your first automated fix does not completely resolve the error, do not attempt a second change. Immediately provide a technical summary of the error log and ask for guidance.

# Technical & Engineering Mandates

## 1. Coding Standards & Defensive Design
* **Explicit & Defensive:** Write robust, type-safe code that actively validates boundaries. Implement defensive error handling (try/catch blocks, explicit exception raising) around all external dependencies and database boundaries.
* **Modular Code Reuse:** Actively scan for opportunities to abstract logic into shared helper functions or utility classes. Avoid duplicate code blocks at all costs.
* **Data Integrity & Parameter Matching:** Python FastAPI Pydantic schemas and raw SQL parameters must explicitly match the exact expected data types, string lengths, and constraints defined in the PostgreSQL database catalog. This prevents silent truncations or type-mismatch execution errors.

## 2. Documentation Style
* **Self-Documenting Standard:** Prioritize clean, expressive variable names and intuitive code flows over verbose comment bloat.
* **Mandatory Headers:** Every new or refactored function, API endpoint, and database stored procedure must feature a clean, concise header docstring block at the top explaining its core purpose, parameters, and return types.

## 3. Database-First Computation (PostgreSQL & PostGIS)
* **Zero Inefficiency:** Minimize Python I/O overhead. All complex transformations, aggregations, spatial track filtering, and segment comparisons must execute within the PostgreSQL layer using native SQL or database stored procedures.
* **No Rogue Refactoring:** You must never alter existing database schemas, spatial parameters, or custom functions without presenting a detailed Pros vs. Cons list to the user first.
* **Parallel Migration Schemas:** All new tables, views, and stored procedures created during the migration must reside in schema copies suffixed with `_migration` (e.g., `activities_migration`, `health_migration`). Legacy schemas (`activities`, `health`, `music`, `staging`, etc.) must remain untouched until the user approves a final cleanup.

## 4. Git, Environments, & Execution Guardrails
* **Git Hands-Off:** You are strictly forbidden from executing `git commit`, `git push`, or modifying the Git staging index. Git management belongs solely to the user.
* **Environment Awareness:** The codebase must dynamically detect its runtime environment (Windows for Local Dev, Linux for Pi 5 Production) using explicit configuration routing (e.g., environment variables or python paths).
* **Local Verification:** All development must be executed, built, and verified locally on the Windows development machine using PowerShell before code can be considered ready for a staging handoff.
* **Production Asset Compilation:** The React frontend must be compiled to static production assets via `npm run build` and served directly by the Python FastAPI backend to minimize active processes on the Pi 5.

# Session Management & Handoff Protocol

## 1. End‑of‑Session Documentation
At the end of every conversation (or when handing off to another agent), you **must** write a handoff note. This ensures continuity and avoids orphaned work.

- **Location:** Append to `memory-bank/activeContext.md` under the "Session Log" section, or create a separate `memory-bank/handoff-notes.md` if you prefer.
- **Content:** Include:
  - **What was completed** (list tasks/ID from `progress.md`).
  - **What remains** (pending tasks, blockers, uncertainties).
  - **Decisions made** (e.g., "We skipped P0-04, using `_migration` schemas").
  - **Next steps** (clear, actionable items for the next agent or the user).
  - **Any risks or open questions** that need user input.

## 2. Update `progress.md` Regularly
After completing a task (or set of tasks), update the corresponding row in `progress.md` to reflect the new status (e.g., change `⏳ Pending` to `✅ Done` or `⏳ In Progress`). This keeps the roadmap accurate.

## 3. Handoff Checklist
Before ending a session, verify:
- [ ] `activeContext.md` (or handoff file) is updated with a summary.
- [ ] `progress.md` reflects the latest status.
- [ ] Any changes made to code or configuration are committed and pushed (if appropriate) – but remember: Git commits are user‑managed, so you may only suggest but not execute `git commit` unless instructed.

## 4. User‑Facing Decisions
If you encounter a question that requires user input (e.g., choosing a library, altering a schema, or deciding on architecture), explicitly note it in the handoff and flag it for the user. Do not proceed autonomously on such decisions.
